# StockWars 성능 목표와 저사양 노트북 검증 계획

> 작성: 2026-10-19. 사용자 노트북을 첫 검증 기기로 삼는다. **P0 (Core) · ✅ 완료: 목표·검증 계획 문서화 / ⏳ 대기: 기기 상세 확인·실측·최적화·게임 검수.** 이 문서는 공식 최소 사양이나 성능 달성 보고서가 아니다.

## 1. 목적과 개발 환경

사용자가 원하는 ‘동숲 정도의 최적화’는 마을이 복잡해져도 움직임이 일정하고, 조작에 바로 반응하며, 오래 플레이해도 느려지지 않는 경험을 지향한다는 의미다. 다른 게임과 동일한 그래픽·성능을 보장하거나 동일한 하드웨어 기준으로 비교한 결과를 뜻하지 않는다.

졸업 전시회까지 현재 웹 클라이언트·Electron 실행 환경을 유지한다. 전시회 이후 Unity 전환은 확정하지 않는다. 실제 병목과 개선 비용을 확인한 뒤 판단하며, 3D 전환만으로 엔진 이전을 필수 작업으로 잡지 않는다. 현재 구조는 [기술 명세](CORE_GDD_06_TechnicalSpec.md)를 따른다.

## 3. 초기 성능 목표

아래는 구현·측정으로 검증할 목표다. 공식 최소/권장 사양은 해당 기기와 추가 비교 기기의 결과를 확보한 후 별도로 정한다.

| 항목 | 초기 목표 | 검증 방법 |
| :--- | :--- | :--- |
| 3D 표시 | 낮은 옵션, 1280×720 수준의 내부 렌더링 해상도 | 실제 렌더 타깃 크기·창 크기·DPR을 함께 기록 |
| 프레임 | 기준 노트북에서 안정적인 30fps | 평균 FPS와 프레임 시간 분포·긴 프레임을 함께 기록 |
| 고성능 설정 | 여유 있는 기기의 60fps 모드는 후속 검토 | 기본 30fps 목표 검증 후 비교 |
| UI 가독성 | 글자·차트·주문표·상품 식별이 선명함 | 실제 화면 배율에서 읽기·선택·드래그 확인 |
| 조작 반응 | 이동·메뉴·상품 배치 시 눈에 띄는 멈춤 최소화 | 입력부터 표시까지 지연과 긴 작업을 확인 |
| 장시간 사용 | 30분 이상 플레이·반복 출입 후 지속적인 성능 악화 없음 | 동일 장면 복귀 시 메모리·프레임 비교 |
| 로딩 | 첫 실행·첫 입장·재입장 시간의 일관성 관리 | 구간별 소요 시간 기록 후 허용 시간 결정 |

30fps의 프레임 간격은 약 33.3ms다. 평균 FPS만으로 통과 판정하지 않고 p95/p99 프레임 시간, 100ms 이상 긴 프레임의 횟수·발생 상황을 기록한다. 100ms는 초기 관찰용 분류 기준이며 확정 허용치가 아니다. 로딩 구간과 일반 플레이 구간은 분리해 분석한다. 지연·메모리·로딩의 정확한 허용치는 첫 실측 후 정한다.

## 4. 제작·최적화 원칙

### 화면과 에셋

- 3D 장면의 내부 해상도와 UI 해상도를 분리한다. 낮은 옵션에서도 글자·차트·주문표를 포함한 전체 화면을 한 장으로 축소하지 않는다. DPR에 따라 3D 해상도가 의도치 않게 증가하지 않는지 확인한다.
- 낮은 옵션은 실시간 그림자·반사·후처리 효과를 최소화한다. 단순 접지 그림자·미리 만든 명암 등은 시각 확인 후 선택하며, 기존 아트를 검수 없이 일괄 교체하지 않는다.
- 같은 소품은 모델·재질·텍스처를 가능한 범위에서 공유한다. 화면 밖 오브젝트 처리, 반복 소품의 묶음 렌더링 등은 측정한 병목에 맞춰 적용한다.
- 모델 복잡도·텍스처 해상도·재질 수·동시 표시 주민 수는 대표 장면에서 측정해 예산을 정한다. 근거 없는 공통 폴리곤 상한이나 텍스처 크기를 지금 확정하지 않는다.
- 에셋 압축은 설치 용량과 전송량, 로딩 후 메모리 사용을 구분해서 검증한다. 파일이 작아졌다고 GPU 메모리까지 같은 비율로 줄었다고 판단하지 않는다.

### 장면과 실행 로직

- 모든 실내·미니게임을 처음부터 활성화하지 않는다. 필요한 자원을 단계적으로 불러오고, 장면을 떠나면 전용 렌더 루프·타이머·이벤트·GPU 자원을 정리한다. 공유 자원과 재입장용 캐시는 소유권·용량을 관리한다.
- 시장·소셜·저장 등 계속 필요한 로직과 비활성 화면의 갱신을 분리한다. 화면을 숨겼다는 이유로 경제 시간·거래·주문 취소 규칙이 달라지지 않게 한다.
- 포장 퍼즐의 제한 시간·손님 화남 상승은 프레임 수에 종속시키지 않는다. 30fps와 60fps에서 같은 시간 규칙이 작동하도록 검증한다.
- 큰 저장 직렬화·대량 DOM 갱신·에셋 해제 때문에 이동이나 상품 드래그가 끊기는지 확인한다. 실제 원인을 찾은 뒤 분할 처리·갱신 빈도 조절 등을 적용한다.

## 5. 측정 절차

1. 대상 노트북에서 빌드 식별자·측정 날짜·GPU/드라이버·OS·전원 모드·전원 연결·창 크기·화면 배율·그래픽 옵션을 기록한다. 첫 기준 측정은 전원 연결 상태로 통일하고 배터리 상태는 별도 비교한다.
2. 배포용 Electron 실행본에서 먼저 확인한다. 브라우저 측정은 원인 분석을 보조하며 Electron 결과를 대체하지 않는다. 개발자 도구를 닫은 체감 측정과 프로파일러를 켠 분석 측정을 구분한다.
3. 첫 실행부터 조작 가능 시점까지 측정한다. 최초 에셋 로딩과 캐시가 있는 재입장을 구분한다.
4. 아래 대표 장면을 같은 경로·조건으로 반복한다. 아직 구현되지 않은 기능은 대기로 표시하고 측정 완료로 기록하지 않는다.
5. 30분 이상 혼합 플레이하고 마을↔실내 출입을 초기 시험 기준 20회 반복한다. 같은 장면에서 잠시 안정된 뒤 메모리를 비교한다. 캐시의 일시 증가와 반복마다 계속 커지는 누수를 구분한다.
6. CPU·프레임·렌더링·메모리 자료로 병목을 좁힌 후 한 종류의 변경을 적용하고 같은 조건에서 비교한다. 시각 품질·저장·상호작용이 훼손되지 않았는지도 확인한다.

| 대표 장면 | 확인할 상황 | 현재 상태 |
| :--- | :--- | :--- |
| 3D 마을 | 건물·나무·주민이 많이 보이는 구간 이동, 카메라 변화 | ⏳ 기준 노트북 실측 대기 |
| 실내 왕복 | 집·증권사 등 입장/퇴장, 재입장 시 자원 재사용 | ⏳ 실측 대기 |
| 시장 UI | 차트·시세 갱신 중 메뉴·주문 조작 | ⏳ 실측 대기 |
| 잡화점 포장 퍼즐 | 상품 드래그·회전, 손님/주문 증가, 화남·퇴장 처리 | ⏳ 구현 후 실측 |
| 우편 | 편지 작성·목록 열람·선물 수령 | ⏳ 구현 후 실측 |
| 저장·온라인 | 자동 저장과 수신 이벤트가 겹치는 상황 | ⏳ 실측 대기 |

전체 콘텐츠 수와 동시에 표시·실행되는 콘텐츠 수를 구분한다. 대표 장면의 오브젝트·주민·효과 수를 결과에 남겨 이후 콘텐츠 증가와 비교한다.

## 7. 우선순위와 다음 단계

- **P0 (Core) · ✅ 완료:** 사용자 기기 확인 정보·30fps 검증 목표·측정 절차 문서화.
- **P0 (Core) · ⏳ 대기:** 실제 GPU·실행 설정 확인, 대상 노트북의 현재 마을·UI 기준 측정, 주요 끊김·누수 원인 수정.
- **P1 (Major) · ⏳ 대기:** 측정 기반 옵션·에셋 예산, 신규 포장/우편 기능 회귀 검증, 추가 기기 비교.
- **P2 (Polish/Post) · ⏳ 대기:** 여유 기기 60fps·고화질 옵션, 추가 시각 효과 검토.

현재는 목표 문서만 작성했다. 성능 측정·최적화 적용·최소 사양 확정 또는 Unity 이전 결정을 완료로 기록하지 않는다.
